# Vitalis — Architecture

## Topology

| Layer | Location | Responsibility |
|---|---|---|
| Web client | `apps/web` | Renders ReportSpec sections, upload UX, review queue, preferences. Holds zero layout logic for reports. |
| API server | `apps/server` | Ingestion pipeline, report compiler, export/retention, auth boundary. |
| Shared contracts | `packages/shared` | zod schemas for every cross-boundary payload. |
| Database | Supabase (Postgres) | Schema + RLS in `supabase/migrations/0001_init.sql`. |
| Object store | Supabase Storage | Raw files in a private `documents` bucket, path `<user_id>/<doc_id>`, signed-URL reads. |

## The ingestion pipeline

```
upload (base64)                         stage 1            stage 2                stage 3
────────────► hash & dedupe ──► tiered OCR ──► classify + extract ──► normalize ──► score ──► persist
                                    │            (domain agent)        │             │
                                    ▼                                  ▼             ▼
                            attempts recorded               alias tables      review queue
                            in extraction_jobs              (mini-LOINC/      if any field
                                                            RxNorm/ICD-10)    < threshold
```

### Stage 1 — tiered OCR (`pipeline/ocr.ts`)

| Tier | When used | Cost | Suggested backing model/service |
|---|---|---|---|
| `tier1_text_layer` | digital PDF / transcript has usable embedded text | ~zero | (none — stdlib parsing) |
| `tier2_classical_ocr` | printed scans, photos of print | ~$0.001/page | Google Document AI, Azure Doc Intelligence, or Tesseract sidecar |
| `tier3_vision_model` | handwriting, stamps, tier-2 confidence < threshold | ~$0.01–0.03/page | GPT-4o / Claude Sonnet vision / Qwen2.5-VL (self-host) |

Escalation policy is evidence-based: tier-2 mean confidence below
`OCR_CONFIDENCE_ESCALATION_THRESHOLD` (default 0.72) escalates; handwriting detection
short-circuits tier 2 entirely. Every attempt (tier, confidence, reason) is stored on
the extraction job, so quality dashboards can decompose accuracy *by tier*.

### Stage 2 — classification + domain-aware extraction (`pipeline/extract.ts`)

One call classifies the document kind (`lab_report`, `prescription`, `discharge_summary`,
`doctor_note`, `radiology_report`, `voice_memo`, `insurance_claim`). A second call runs
the kind-specific extraction prompt. Each kind has curated clinical guidance (sig-code
expansion for prescriptions, "don't unit-convert" for labs, impression-vs-finding rules
for radiology). Output must match `extractionResultSchema` — invalid JSON or schema
violations fail the job; nothing partial is persisted.

### Stage 3 — normalization + confidence gating (`pipeline/normalize.ts`)

Aliases resolve to canonical concepts (`HbA1c`/`glycated hemoglobin` → `hba1c`), missing
reference ranges fill from the registry, lab flags compute deterministically. Fields
below `FIELD_CONFIDENCE_REVIEW_THRESHOLD` (default 0.80) push the whole document to
`needs_review`; the user confirms facts in the UI, flipping them to `human_verified`.
Document status derives from fact states — a document "graduates" to `processed` when
all its facts are verified.

## The generative report compiler (`report/compiler.ts`)

Three inputs, one spec:

1. **Persona** — derived deterministically: age band from DOB; tags from active
   conditions (`diabetic`, `hypertensive`, `hypothyroid`, …) and out-of-range labs
   (`prediabetes_risk` when HbA1c ≥ 5.7 without a diabetes diagnosis).
2. **Preferences** — the user's explicit focus areas, detail level, language, trend
   toggles.
3. **Records + documents** — the verified fact store.

A rule table maps `(kind, basePriority, focusArea?, applies, build, rationale)`.
Rules select which sections exist; persona tags choose which lab analytes trend;
focus areas re-rank priorities; `detailLevel: at_a_glance` trims to essentials.
Every section carries `rationale` — a plain-language audit of *why it was included* —
rendered under each section title.

The frontend is a pure renderer: `SectionCard` looks up `section.kind` in a component
registry. Unknown kinds degrade to a JSON `<details>` view, so new section types can
ship server-side first.

**Downloads**: `report/render.ts` compiles the same spec to self-contained HTML
(inline CSS, print stylesheet, no scripts) — the artifact is generated by our system,
not scraped from the DOM, and prints cleanly to PDF from any browser.

## Data model (Supabase)

```
auth.users
  └── profiles            (identity prefs, display prefs jsonb, retention jsonb)
  └── documents           (kind, status, content_hash, raw_text, ocr_tier)
  │     └── extraction_jobs           (tier, model, confidences, audit)
  │     └── medications  conditions  lab_results  vitals  allergies
  │         (all: document_id FK cascade, confidence, verification)
  └── report_specs        (compiled ReportSpec jsonb)
  └── audit_log           (exports, deletes, verifications — append-only for users)
```

RLS: `auth.uid() = user_id` on every table. The server uses the service role for
pipeline writes; user-scoped reads/writes work from the client with the anon key too.

## Auth boundary

Routes take `:userId` explicitly (`/api/users/:userId/...`). With Supabase Auth wired
in, a middleware verifies the JWT and overrides/extracts `sub` — the handlers and store
layer need no change. See `docs/IMPROVEMENTS.md`.

## Trust & safety invariants

- LLM output never bypasses zod validation.
- Facts always carry `documentId` — delete a document, its facts cascade.
- Exports and deletions are audit-logged *before* execution.
- Training-data consent defaults to **off**.
- A visible non-negotiable disclaimer ships inside every report artifact.
